## 交付包是否应包含 .git（结论：否）

用户询问是否要把 `.git` 打进 `website-handoff.zip`。**结论是不打**，三条理由：

1. **体积**：`.git` 1.2 MB / 93 文件，与整个 `site/` 相当，打进去体积近乎翻倍，
   且多为不可读的二进制（对象库、索引）。
2. **跨机器不可靠（最关键）**：`.git/index` 记录文件路径、mtime、权限位。跨 OS 解压后
   会被判定为"整个工作区被改动"；双方各自提交再合并还会产生对象冲突。Git 的价值是
   **增量历史**，脱离原本地环境易失真。
3. **与用途不符**：用户是纯本地版本管理，异地的历史对本机仓库无帮助。

**替代方案**：包内只放工作区文件（含 `.gitignore` / `.gitattributes`），
对方解压后 `git init -b main && git add -A && git commit` 一次即成。
若确需连历史交接，用 `git bundle create handoff.bundle --all`，对方 `git clone handoff.bundle`。

## 回档规程文档（AGENTS.md §5.0b）

用户提问：文件在多个 agent 间流转时，回档需不需要自己进文件操作代码。

**核心结论**：取决于粒度。粗粒度可由 agent 做，细粒度必须用户在场。

### 五级风险分级（已写入 AGENTS.md §5.0b）
| 级别 | 操作 | 执行人 |
|---|---|---|
| 1 | `git checkout .` 丢弃未提交改动 | agent 可自主 |
| 2 | `git revert <hash>` 撤销某次提交（最安全，留记录） | agent 可自主 |
| 3 | `git switch -c 试验 <hash>` 开分支看历史（**禁止直接 checkout 造成 detached HEAD**） | agent 可自主 |
| 4 | `git reset --hard <hash>` 强行退回 | **必须先获用户同意** |
| 5 | 只回退某几行 / 撤销中间提交（需 rebase 或逐行取舍） | **只分析不动手，用户亲自操作** |

### 写给 agent 的 5 条硬性要求
1. 回档前先 `git status` + `git log --oneline`，把状态报给用户
2. 1–3 级自主；4 级先问；5 级只读分析
3. 回档前先 `git stash` 或开 `backup-YYYYMMDD` 分支存一份
4. 用户未明确要求时，永不执行 `reset --hard` / `push --force` / `clean -fd` / `rebase`
5. 回档后必须复验（build_pages.py + 断链检查 + 双端截图）

### 三张安全网（写进文档）
未提交改动（`checkout .`）/ `reflog`（HEAD 移动记录，能救回"已删"提交）/
`stash`（暂存改动）。其中 reflog 尤其重要——`reset --hard` 丢掉的提交通常仍可找回。

### 实测验证（全部通过）
备份分支创建与删除、reflog 可见性、试验分支开合（不过夜 detached HEAD）、
分支清理均正常。当前仓库：分支 1 个（main），工作区干净。
